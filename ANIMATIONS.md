# Animations for the FoCS slips: ideas

From a read through `slips/lecture*/lecture*.md`. Ideas only, not a plan.

## What the slips already do

- **Reveal step by step with `{pause}`.** This is everywhere (573 uses).
  The warm-up questions already follow "ask, pause, reveal", which is the
  predict-then-reveal pattern in its simplest form.
- **Image sequences.** Lecture 4's making change uses 13 + 8 hand-drawn SVG
  steps placed inline, with a `{pause}` between each.
- **Scripts on a step.** `{pause exec}` with a `slip-script` block that
  swaps images or calls `xOcaml.setHighlight(...)`, and
  `slip.onUndo(...)` to go back. Examples: lecture 7's BST before/after
  (`dict1.png` → `dict2.png`), lecture 6's exception handler picture, and
  lecture 10's highlight in `nbreadth`.
- **One interactive SVG:** lecture 10's game tree (`game-tree.svg` with a
  `toggleKingBranch()` function).
- **Static traces in LaTeX `eqnarray`/`aligned`:** `nrev`, `rev_app`
  (lecture 3), `nbreadth` (lecture 10), `get 2 (from 6)` (lecture 9),
  `nsum`/`summing` (lecture 2).
- **Repeated static images:** `traversal.png` appears five times in
  lecture 7. `llist1–8.png` (lecture 11) and `array1.png` (lecture 7) are
  static.

So slipshow already has what animation needs: **a step model, scripts that
run on a step, and undo.** What's missing is reusable *drawing* for lists,
trees, queues and references, and a way for readers to **predict** when
nobody is presenting.

## Four levels of effort

| Level | What | Cost |
|---|---|---|
| 0 | Reveal the existing traces one line at a time, with a prediction pause ("what's the next line?") and the redex highlighted | Markdown edits only |
| 1 | A `<focs-trace>` element: hand-written steps with the redex marked. Each slip step reveals the next one. A **predict mode** for readers withholds the next step until they choose an option or type it | Small element, steps written by hand |
| 2 | **Data-structure views driven by real execution** in x-ocaml: box-and-pointer lists that show sharing, trees with visit highlights, queues, stacks and ref cells. The code sends events from instrumentation (as in `EXERCISES.md`) to a display element | One renderer, reused everywhere |
| 3 | Traces generated by a **stepper** | Research (`research/stepper.md`, pending) |

How they'd work with slipshow: `{pause exec}` → `el.step()` plus
`slip.onUndo(() => el.back())`, the same pattern the slips already use.

- **In lectures**, a prediction is a pause with a question on screen: ask the
  room, maybe let neighbours discuss, then step.
- **For readers**, the element holds back the reveal until they've
  answered.

## By lecture, with where each idea would go

Best value is marked ★.

### Lecture 2: recursion and complexity

- ★ **`nsum` vs `summing`, side by side.** The `nsum` expression grows
  wider as additions wait (shown as a bar labelled "pending work / stack"),
  while `summing` stays the same width. It makes "iterative" visible, and
  sets up the tail-call check in the exercises. *Level 1, later 3.*
- **`sillySum` call tree** growing to 2ⁿ nodes, with a call counter, next to
  `power`'s log n depth. *Level 2.*
- **Interactive growth table:** pick the time budget (second, minute, hour)
  and see the largest n per complexity class. Have students guess first,
  given what's known about students' firm beliefs about performance.

### Lecture 3: lists

- ★ **`rev_app` as two lists**, `xs` and `acc`, with one element moving
  across per step. This is the canonical "reversal" animation. Prediction:
  "what's `acc` after the next step?" One wrong option shows the order not
  reversing, a common mistake. *Level 1 or 2.* (Agent prototype B6 is
  building this one.)
- ★ **`nrev` shown as copying:** each `@` visibly copies its left list, with
  a running count of copied cells (1 + 2 + … + n), next to the `eqnarray`
  trace that's already there. The O(n²) stops being an abstract claim.
  *Level 2.*
- **`xs @ ys` sharing:** the cells of `xs` are copied and `ys` is pointed to,
  not copied. This is where students first see that immutable data is
  shared. *Level 2.*
- `nlength` vs `addlen`: the same accumulator story as `nsum`/`summing`.

### Lecture 4: more lists, making change

- **`take`/`drop` sharing:** `drop` returns a pointer into the original,
  `take` copies. *Level 2.*
- ★ **Making change as a search tree generated from the real code**,
  replacing the 21 hand-drawn SVGs. The same renderer then covers lecture 6's
  backtracking and lecture 10's search. Prediction: "which branch is tried
  next?" *Level 2.*
- `zip`/`unzip`: small, and probably fine as it is.

### Lecture 5: sorting

- **Insertion sort:** `ins` walking down the sorted part, with a comparison
  counter. Then run it on sorted vs reversed input: linear vs quadratic.
- **Quicksort:** turn the existing `quick_divide/conquer/combine.svg`
  diagrams into a step-through on real data. Then the worst case on sorted
  input.
- **Mergesort:** the split tree, then merging back up.
- Good sorting animations exist elsewhere, so this is lower priority, *unless*
  it's driven by the student's own code (Level 2) with the counter visible.

### Lecture 6: datatypes, exceptions, trees

- ★ **Exception unwinding:** a stack of active handlers grows as `try` blocks
  are entered, and `raise` jumps to the nearest matching one. This replaces
  the static `install_exn_handler.svg`. Then **change with backtracking**:
  the search tree pruning back when `raise` fires. It shares the renderer
  with lecture 4. *Level 2.*
- **Draw any tree value automatically:** evaluating a cell that builds
  `Br(...)` draws the tree. That would retire `tree1.png` and similar
  hand-drawn pictures across lectures 6, 7 and 10. *Level 2, simple.*

### Lecture 7: dictionaries and functional arrays

- ★★ **BST `update` with path copying.** Today it swaps `dict1.png` for
  `dict2.png`. Instead: show old and new trees together, with **new nodes
  highlighted along the search path** and unchanged subtrees *shared* by both
  roots. This is the key idea of persistent data structures, and it's the
  answer to "isn't immutability wasteful?" *Level 2.*
- ★ **Traversals:** replace the five copies of `traversal.png` with one tree
  where nodes light up in visiting order and the output list builds
  alongside. Prediction: "which label comes next?" Then pre-, in- and
  post-order **side by side on the same tree**. Then `preord` with an
  accumulator, without `@`. *Level 1 or 2.*
- ★ **Functional array lookup:** the subscript's binary digits pick left or
  right at each level, animated over `array1.png`'s tree. Tick 3 is about
  this, and lecture 11 has a "Tick 3 hint!" slide, a sign students find it
  hard.
- **Unbalanced trees:** insert sorted keys and watch the tree turn into a
  list.

### Lecture 8: functions as values

- **Matrix transpose with `map hd` / `map tl`:** columns peel off and become
  rows. `matmultpic.png` is static at the moment. It's also a "structural"
  composition of higher-order functions, which Krishnamurthi's work finds
  students struggle with.
- Partial application (`insort (<=)`): a "function with one slot filled"
  picture. Probably more effort than it's worth.

### Lecture 9: lazy lists

- ★ **Thunks being forced:** in `get 2 (from 6)`, the tail shows as a grey
  `fun () -> …` box that turns into a `Cons` cell only when `get` forces it.
  It makes laziness visible, rather than leaving it in the static `aligned`
  trace. *Level 1 or 2.*
- **`interleave`:** the course page already has a separate
  `interleave_explanation.html`, a sign this is a sticking point. A good
  candidate for the same element.
- Call-by-name vs call-by-need: the same expression forced twice, recomputed
  in one and remembered in the other.
- Newton–Raphson: an interactive convergence plot, which could replace
  `nr.png`.

### Lecture 10: queues and search

- ★ **BFS vs DFS on the same tree**, with the **queue or stack contents
  visible** at each step. The slide already highlights `nbreadth`'s
  `ts @ [t; u]` and has a trace. Animate the tree and the queue together.
  Prediction: "what's in the queue now?" *Level 2.*
- ★ **The efficient functional queue:** front and back lists, adding to the
  back, taking from the front, and the occasional reversal. Show the
  even-out-over-time cost with a running counter. *Level 2.*
- **Iterative deepening:** the depth limit growing, with the re-explored
  nodes shaded to show the repeated work.
- The game tree is already interactive. It could share the tree renderer.

### Lecture 11: procedural programming

- ★ **Ref cells as boxes, driven by the code:** `let r = ref 0`, `r := !r + 1`,
  aliasing (`let s = r`), and `swap r r`. Replace `llist1–8.png` with the
  mutable list being built live as `extend last "y"` runs. This is where the
  SMoL misconceptions are, so predictions with distractors drawn from
  misconceptions fit well here. *Level 2.*
- **Bank accounts:** two closures, each holding its own private ref, so the
  environment is visible.
- **A `while` loop as a table of variable values**, one row per iteration.

## What to build, for the most use from the least work

**One Level 2 renderer** with three views (lists with sharing, trees with
highlights, refs/queues as boxes), plus **one stepping and prediction
wrapper** that plugs into slipshow's `step`/`onUndo`. Between them they
cover almost every ★ item above:

| Renderer view | Covers |
|---|---|
| Lists with sharing | L3 `rev_app`, `nrev` copying, `@` sharing · L4 `take`/`drop` · L9 thunks (cells that may be unforced) · L10 queue |
| Trees with highlights | L6 auto-drawn trees · L7 traversals, BST path copying, functional arrays · L10 BFS/DFS · L4/L6 search trees for change |
| Boxes / refs | L11 refs, aliasing, mutable lists, closures |

Level 1 (`<focs-trace>`) is still worth having for expression-rewriting
traces (`nsum`, `get`, `nbreadth`) until a stepper exists.

**Suggested order:** `rev_app` (lists, the simplest) → traversals (trees) →
BST path copying (trees with sharing, the most valuable) → BFS/DFS with the
queue → refs and aliasing → thunks.

## Open questions

- Is there a slipshow "reader mode", for students reading on their own, in
  which the element should wait for a prediction rather than just stepping?
- Should predictions be **anonymous polls** in lectures? A show of hands is
  fine. Anything that collects responses electronically would need a server,
  which goes against the local-only principle.
- The drawings must be legible on the lecture projector and in dark mode. The
  slips' `extra.css` has a style the renderer should follow.
